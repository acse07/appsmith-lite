# AppSmith Lite — Technical Specification v1.0

**Тип:** Low-code / Internal Tools Builder
**Frontend:** Next.js App Router + React + TypeScript
**Backend:** Next.js Route Handlers + Server Functions
**Database:** PostgreSQL + Prisma
**Архитектура:** модульный монолит
**Цель:** сильное Junior+/Middle Frontend портфолио

---

## 1. Назначение системы

AppSmith Lite предоставляет визуальный конструктор веб-приложений для внутренних процессов компаний.

Пользователь может создать проект, добавить страницы, разместить UI-компоненты, настроить их свойства, связать компоненты с данными, выполнить действия по нажатию кнопок и опубликовать приложение.

### Основной пользовательский сценарий

1. Пользователь регистрируется.
2. Создаёт workspace.
3. Создаёт приложение `Sales Dashboard`.
4. Открывает визуальный редактор.
5. Добавляет таблицу и форму.
6. Настраивает источник данных.
7. Связывает таблицу с результатом API-запроса.
8. Настраивает отправку формы.
9. Проверяет приложение в Preview.
10. Публикует приложение.
11. Открывает опубликованную версию без элементов редактора.

### Принцип архитектуры

Сам редактор и готовые приложения должны использовать одну структуру описания интерфейса, но разные режимы работы:

- Editor — редактирование дерева компонентов.
- Preview — проверка черновика с настоящими действиями.
- Published — выполнение неизменяемой опубликованной версии.

---

## 2. Роли пользователей

На первом этапе достаточно трёх ролей.

| Роль   | Возможности                                                   |
| ------ | ------------------------------------------------------------- |
| Owner  | Управляет workspace, участниками, приложениями и публикациями |
| Editor | Создаёт и редактирует приложения, настраивает запросы         |
| Viewer | Открывает доступные опубликованные приложения                 |

Один пользователь может состоять в нескольких workspace с разными ролями.

Любое изменение данных должно проверяться на сервере. Скрытие кнопок в интерфейсе не считается механизмом безопасности.

## 3. Функциональные модули

### Модуль A. Authentication

Требования:

- Регистрация по email и паролю.
- Вход и выход.
- Защищённые маршруты.
- Хранение пользовательской сессии.
- Проверка прав доступа.
- Возможность подключить OAuth позднее.

Критерии готовности:

- Неавторизованный пользователь не открывает редактор.
- Пользователь не получает доступ к чужому workspace через подмену URL.
- Выход из аккаунта завершает сессию.

### Модуль B. Workspace Dashboard

Возможности:

- Создание workspace.
- Просмотр списка приложений.
- Создание и удаление приложения.
- Переименование.
- Дублирование приложения.
- Сортировка по дате изменения.
- Поиск по названию.
- Информация о статусе: Draft / Published.

Интерфейс:

- Sidebar со списком приложений.
- Карточки приложений.
- Кнопка Create App.
- Меню действий.
- Empty, loading и error states.

### Модуль C. Visual Editor

Главный функциональный модуль.

Редактор состоит из пяти областей:

**1. Верхняя панель**

- Название приложения.
- Название страницы.
- Индикатор сохранения.
- Undo / Redo.
- Переключение Desktop / Tablet / Mobile.
- Preview.
- Publish.

**2. Левая панель компонентов**

Каталог доступных компонентов с поиском и группировкой.

**3. Дерево элементов**

Иерархия компонентов текущей страницы. Возможность выбирать элементы, менять порядок и раскрывать вложенные контейнеры.

**4. Центральный canvas**

Рабочая поверхность с размещением компонентов и визуальным выделением выбранного элемента.

**5. Правая панель свойств**

Настройки выбранного компонента, разделённые на Content, Style и Events.

#### Обязательные операции

- Добавить компонент через drag-and-drop.
- Добавить компонент нажатием в каталоге.
- Выбрать элемент на canvas или в дереве.
- Переместить компонент внутри контейнера.
- Изменить порядок соседних элементов.
- Изменить свойства.
- Дублировать компонент.
- Удалить компонент.
- Скопировать и вставить.
- Отменить и повторить изменение.
- Сохранить и восстановить черновик.

**Ограничение MVP:** реализовать layout на CSS Grid/Flex, а не свободное позиционирование каждого пикселя, как в Figma. Это существенно снижает сложность первой версии.

### Модуль D. UI Component Registry

Каждый компонент должен иметь описание:

- `type` — уникальный тип.
- `displayName` — название.
- `defaultProps` — исходные свойства.
- `propsSchema` — схема валидации.
- `allowedChildren` — разрешённые вложенные элементы.
- `events` — поддерживаемые события.
- `render` — способ отображения.

#### Компоненты MVP

| Компонент | Настройки                         |
| --------- | --------------------------------- |
| Text      | Текст, размер, цвет, жирность     |
| Heading   | Текст, уровень заголовка          |
| Button    | Текст, вариант, disabled, onClick |
| Input     | Label, placeholder, required      |
| Select    | Options, defaultValue, label      |
| Container | Direction, gap, padding           |
| Table     | Columns, data, pagination         |
| Form      | Fields, validation, onSubmit      |
| Chart     | Type, data, xAxis, yAxis          |
| Divider   | Orientation, thickness            |

Для MVP достаточно реализовать первые 7 компонентов, а Form и Chart добавить при развитии проекта.

Компоненты должны поддерживать состояния loading, empty и error там, где они необходимы.

### Модуль E. Property Inspector

При выборе компонента справа появляется форма настройки.

Например, для Button:

- Label.
- Variant: Primary / Secondary / Outline.
- Size: Small / Medium / Large.
- Disabled.
- Width.
- Background.
- Click Action.

При изменении свойства центральный canvas обновляется сразу.

Требования:

- Изменения проходят через единый editor store.
- Inspector строится на базе схем компонентов.
- Нельзя записать несовместимое свойство.
- Изменения участвуют в Undo/Redo.
- Выделение элемента не должно менять содержимое документа.

### Модуль F. Data Sources

Пользователь может создавать именованные запросы:

- `getCustomers`
- `getOrders`
- `createCustomer`
- `updateCustomer`

Поддержка в MVP:

- Встроенные mock-данные.
- REST GET/POST к разрешённым источникам.
- Заголовки запроса.
- JSON body.
- Query parameters.
- Test Request.
- Отображение результата.
- Binding результатов к компонентам.

Необходимо раздельно хранить:

1. Конфигурацию источника.
2. Конфигурацию конкретного запроса.
3. Результат выполнения.
4. Статус loading/error.
5. Секреты источника, если они появятся позднее.

В MVP использовать предварительно разрешённые публичные тестовые API и mock-источники. Произвольные URL и приватные токены не разрешать до реализации защищённого серверного слоя.

### Модуль G. Data Binding

Компоненты должны получать данные динамически.

Примеры:

- Таблица использует `queries.getCustomers.data`.
- Заголовок использует `app.name`.
- Текст использует `state.selectedCustomer.name`.
- Кнопка становится disabled при `queries.saveCustomer.isLoading`.

Сначала реализовать декларативные привязки по безопасным путям, без выполнения пользовательского JavaScript.

Например:

`{ "kind": "binding", "path": "queries.getCustomers.data" }`

Требования:

- Разрешение пути из runtime context.
- Проверка допустимых источников.
- Обработка отсутствующих данных.
- Проверка типов.
- Обнаружение циклических зависимостей для вычисляемых значений.
- Сообщение об ошибке привязки.
- Кеширование вычислений при необходимости.

### Модуль H. Event & Action Engine

Компоненты генерируют события:

- onClick.
- onChange.
- onSubmit.
- onRowSelect.

Возможные действия:

- Navigate.
- SetValue.
- RunQuery.
- ShowToast.
- ResetForm.
- OpenModal — после добавления Modal.

Пример сценария:

`Button.onClick → RunQuery(createCustomer) → ShowToast`

На первом этапе допускается одна операция на событие. Затем добавить цепочки последовательных действий, ветвление успех/ошибка и отмену выполнения.

Нельзя выполнять строку JavaScript через `eval`, `new Function` или другой механизм динамического выполнения.

### Модуль I. Preview & Runtime

Preview и Published должны использовать общий `RuntimeRenderer`.

В режиме Preview:

- Отключены элементы выделения.
- Drag-and-drop не работает.
- Компоненты интерактивны.
- Формы валидируются.
- Запросы могут выполняться.
- Ошибки отображаются пользователю.

При переходе обратно в Editor черновик не должен теряться.

### Модуль J. Publish & Versioning

MVP должен поддерживать:

- Сохранение черновика.
- Создание опубликованной версии.
- Просмотр опубликованного приложения.
- Изменение черновика без изменения опубликованной версии.
- Повторную публикацию.

Рекомендуемая модель:

- `Page.document` — текущий черновик.
- `AppVersion.snapshot` — неизменяемый снимок опубликованного приложения.
- `Application.publishedVersionId` — ссылка на активную версию.

В MVP опубликованные приложения доступны только авторизованным участникам workspace.

Публичный доступ по ссылке — отдельная будущая возможность с собственными правилами безопасности.

- Runtime не зависит от визуальных инструментов редактора.
- Изменения документа выполняются через editor commands.

## 6. Модель документа редактора

Основная идея: **интерфейс описывается данными, а не сохранённым JSX**.

Внутри приложения хранится дерево компонентов.

Пример документа:

```json
{
  "schemaVersion": 1,
  "rootId": "root",
  "nodes": {
    "root": {
      "id": "root",
      "type": "Container",
      "props": {
        "direction": "column",
        "gap": 16
      },
      "children": ["heading-1", "button-1"]
    },
    "heading-1": {
      "id": "heading-1",
      "type": "Heading",
      "props": {
        "text": "Customer Dashboard",
        "level": 2
      },
      "children": []
    },
    "button-1": {
      "id": "button-1",
      "type": "Button",
      "props": {
        "label": "Load customers"
      },
      "children": [],
      "events": {
        "onClick": {
          "type": "runQuery",
          "queryId": "query-1"
        }
      }
    }
  }
}
```

Для каждого UI Node:

```ts
type NodeId = string;

type UIComponentType =
  | 'Container'
  | 'Text'
  | 'Heading'
  | 'Button'
  | 'Input'
  | 'Select'
  | 'Table'
  | 'Form'
  | 'Chart'
  | 'Divider';

interface UINode {
  id: NodeId;
  type: UIComponentType;
  props: Record<string, unknown>;
  children: NodeId[];
  events?: Record<string, ActionConfig>;
}

interface UIDocument {
  schemaVersion: number;
  rootId: NodeId;
  nodes: Record<NodeId, UINode>;
}
```

`ActionConfig` реализовать как discriminated union, отдельно для каждого типа действия.

### Инварианты дерева

- Каждый ID уникален.
- Корневой элемент существует.
- У корня нет родителя.
- Элемент не может быть родителем самого себя.
- Циклы запрещены.
- У любого некорневого элемента ровно один родитель.
- Дочерние элементы существуют.
- Тип дочернего компонента допустим для контейнера.
- В дереве нет потерянных узлов.
- Максимальная глубина и количество элементов ограничены.
- `schemaVersion` проверяется перед загрузкой.

### Editor Commands

Обязательные команды:

```ts
addNode(parentId, node, index)
removeNode(nodeId)
moveNode(nodeId, parentId, index)
updateNodeProps(nodeId, patch)
duplicateNode(nodeId)
selectNode(nodeId)
undo()
redo()
```

Команды изменения документа должны быть независимы от React-компонентов.

Рекомендуется делать операции чистыми функциями: входной документ + команда → новый документ.

Выделение, открытые панели и текущий zoom должны храниться отдельно от документа.

## 7. Состояние приложения

Не следует складывать абсолютно всё в один глобальный Zustand store.

### Editor State

- Текущий документ.
- Выбранный элемент.
- Активный инструмент.
- Undo/Redo history.
- Режим canvas.
- Состояние перетаскивания.
- dirty / saving / saveError.

### Server State

Через TanStack Query:

- Список workspace.
- Список приложений.
- Данные приложений.
- Конфигурации запросов.
- История версий.

### Runtime State

- Значения Input/Select/Form.
- Данные выполненных запросов.
- loading/error по каждому запросу.
- Временные переменные приложения.
- Состояние выбранных строк таблицы.

### Правило

Во время drag-and-drop нельзя отправлять каждое движение на сервер.

Изменения выполняются локально, а затем сохраняются с debounce.

Например, после 800 мс без новых изменений. Это проектное значение, которое можно настроить.

### Связи

```text
User
 └── WorkspaceMember
      └── Workspace
           ├── Application
           │    ├── Page
           │    ├── AppQuery
           │    └── AppVersion
           └── DataSource
```

### Важные ограничения

- `publishedVersionId` должен ссылаться на версию того же приложения.
- При создании версии snapshot должен содержать страницы и необходимые конфигурации запросов.
- Секретные значения запрещено хранить в JSON, отправляемом клиенту.
- Удаление workspace и приложений должно иметь продуманную стратегию каскадного удаления.
- Конфигурации JSONB валидируются Zod перед записью и после чтения.
- Индексы создаются по фактическим сценариям выборки.

## 9. API Contracts

Базовый префикс: `/api`

### Workspaces

| Method | Endpoint          | Описание            |
| ------ | ----------------- | ------------------- |
| GET    | `/workspaces`     | Доступные workspace |
| POST   | `/workspaces`     | Создать workspace   |
| GET    | `/workspaces/:id` | Детали              |
| PATCH  | `/workspaces/:id` | Изменить            |
| DELETE | `/workspaces/:id` | Удалить             |

### Applications

| Method | Endpoint               | Описание            |
| ------ | ---------------------- | ------------------- |
| GET    | `/workspaces/:id/apps` | Список приложений   |
| POST   | `/workspaces/:id/apps` | Создать             |
| GET    | `/apps/:appId`         | Получить            |
| PATCH  | `/apps/:appId`         | Изменить метаданные |
| DELETE | `/apps/:appId`         | Удалить             |

### Pages

| Method | Endpoint                     | Описание           |
| ------ | ---------------------------- | ------------------ |
| GET    | `/apps/:appId/pages`         | Список страниц     |
| POST   | `/apps/:appId/pages`         | Создать страницу   |
| GET    | `/apps/:appId/pages/:pageId` | Загрузить документ |
| PUT    | `/apps/:appId/pages/:pageId` | Сохранить документ |
| DELETE | `/apps/:appId/pages/:pageId` | Удалить            |

### Queries

| Method | Endpoint                                | Описание        |
| ------ | --------------------------------------- | --------------- |
| GET    | `/apps/:appId/queries`                  | Список запросов |
| POST   | `/apps/:appId/queries`                  | Создать запрос  |
| PATCH  | `/apps/:appId/queries/:queryId`         | Изменить        |
| DELETE | `/apps/:appId/queries/:queryId`         | Удалить         |
| POST   | `/apps/:appId/queries/:queryId/execute` | Выполнить       |

### Publishing

| Method | Endpoint                           | Описание        |
| ------ | ---------------------------------- | --------------- |
| POST   | `/apps/:appId/publish`             | Опубликовать    |
| GET    | `/apps/:appId/versions`            | Список версий   |
| GET    | `/apps/:appId/versions/:versionId` | Получить версию |

Route Handlers должны применять:

1. Проверку сессии.
2. Проверку workspace membership.
3. Проверку роли.
4. Валидацию параметров.
5. Вызов service.
6. Возврат единого response format.

### Пример обновления страницы

Request:

```json
{
  "document": {
    "schemaVersion": 1,
    "rootId": "root",
    "nodes": {
      "root": {
        "id": "root",
        "type": "Container",
        "props": {},
        "children": []
      }
    }
  },
  "expectedRevision": 4
}
```

Response:

```json
{
  "data": {
    "pageId": "page-123",
    "revision": 5,
    "savedAt": "2026-10-09T10:00:00Z"
  }
}
```

При несоответствии `expectedRevision` сервер отвечает `409 Conflict`.

Это защищает от незаметной перезаписи изменений из другой вкладки.

### Формат ошибок

```json
{
  "error": {
    "code": "REVISION_CONFLICT",
    "message": "Page has been modified",
    "details": {}
  }
}
```

Стандартные статусы: 400, 401, 403, 404, 409, 422, 429, 500.

## 10. Безопасность

Этот проект позволяет пользователю настраивать API-запросы, поэтому безопасность является отдельным архитектурным требованием.

### Обязательно

- Проверять авторизацию и роль на каждом серверном действии.
- Не доверять workspaceId и appId из клиента.
- Валидировать пользовательский JSON и URL.
- Ограничивать размер документов, запросов и ответов.
- Не отдавать приватные ключи и токены браузеру.
- Не использовать `eval`, `new Function` и небезопасный HTML.
- Использовать HTTPS в production.
- Установить CSP и необходимые защитные заголовки.
- Ограничивать частоту выполнения API.
- Не выводить секреты в логах.
- Не допускать доступа к чужим данным.

### Защита от SSRF

В MVP proxy должен поддерживать только заранее разрешённые адреса источников.

Для расширенной версии:

- Проверять протокол.
- Запрещать внутренние, loopback и link-local адреса.
- Проверять DNS-результаты.
- Контролировать redirects.
- Ограничивать порты и домены.
- Использовать egress-фильтрацию.
- Вводить таймауты и ограничения ответа.

Запретить обращения к внутренним сервисам, метаданным облака и приватной инфраструктуре.

Подключение API — потенциально опасная возможность. Не реализовывать открытый proxy без защиты.

## 11. Сложные frontend-задачи

### Задача 1. Nested Drag-and-Drop

Реализовать:

- Перемещение элементов между контейнерами.
- Подсветку допустимой зоны.
- Запрет недопустимой вложенности.
- Автоматическую прокрутку.
- Отмену операции через Escape.
- Перестановку элементов без дублирования ID.

Особый случай: нельзя перетащить контейнер внутрь самого себя или собственного потомка.

### Задача 2. Undo/Redo

История должна корректно работать с:

- Добавлением элемента.
- Удалением элемента.
- Изменением свойства.
- Перестановкой.
- Дублированием.

Выделение элемента не включать в историю документа.

Предусмотреть лимит истории, например 50 изменений.

### Задача 3. Schema-driven Inspector

Создать реестр property editors:

- string → TextInput.
- number → NumberInput.
- boolean → Switch.
- enum → Select.
- color → ColorPicker.
- binding → BindingEditor.

При добавлении нового UI-компонента Inspector должен появляться преимущественно за счёт его схемы, без отдельной большой формы на каждый компонент.

### Задача 4. Renderer Engine

Создать рекурсивный renderer, который:

- Получает `UIDocument`.
- Проверяет типы.
- Находит React-компонент в registry.
- Применяет props и bindings.
- Рендерит children.
- Подключает event handlers.

Не использовать динамическую генерацию JSX-кода на сервере.

### Задача 5. Data Binding Engine

Разрешение значений вида:

`queries.getCustomers.data`

`state.customerName`

`inputs.email.value`

Должно быть устойчивым к отсутствующим путям, неправильным типам и ошибкам запроса.

### Задача 6. Производительность

- Изменение Input не должно перерисовывать весь canvas.
- Не создавать новые объекты props без необходимости.
- Использовать селекторы Zustand.
- Мемоизировать тяжёлые компоненты.
- Виртуализировать большие таблицы и списки.
- Измерять производительность React Profiler.
- Сократить количество сетевых запросов при автосохранении.

## 12. Тестирование

### Unit — Vitest

Обязательные тесты:

- `addNode` добавляет компонент.
- `removeNode` удаляет поддерево.
- `moveNode` перемещает компонент.
- Перенос контейнера в собственного потомка запрещён.
- `duplicateNode` создаёт новые ID для всего поддерева.
- Undo восстанавливает предыдущее состояние.
- Redo возвращает отменённое изменение.
- Binding resolver корректно обрабатывает отсутствующее значение.
- Document validator обнаруживает циклы.
- Неверный `schemaVersion` отклоняется.

### Component — Testing Library

- Property Inspector обновляет компонент.
- Palette показывает список.
- Canvas выделяет нужный элемент.
- Ошибка API отображается.
- Table показывает данные.
- Button запускает зарегистрированное действие.
- Preview скрывает инструменты редактора.

### Integration

- Сохранение страницы увеличивает revision.
- При конфликте revision возвращается 409.
- Пользователь из другого workspace получает отказ.
- Publish создаёт неизменяемую версию.
- Query execution проверяет права и разрешённый источник.

### E2E — Playwright

Сценарий 1: Create Application

1. Войти.
2. Создать workspace.
3. Создать приложение.
4. Открыть редактор.
5. Добавить Heading.
6. Изменить текст.
7. Обновить страницу.
8. Проверить сохранение.

Сценарий 2: Publish Application

1. Создать страницу.
2. Добавить кнопку и текст.
3. Открыть Preview.
4. Опубликовать.
5. Открыть Runtime.
6. Проверить отображение и действие.

Сценарий 3: Authorization

1. Создать два workspace с разными участниками.
2. Авторизоваться под пользователем второго.
3. Попытаться открыть чужое приложение.
4. Проверить ответ 403/404 без утечки данных.

Сценарий 4: Revision Conflict

1. Открыть приложение в двух вкладках.
2. Изменить обе копии.
3. Сохранить первую.
4. Попытаться сохранить вторую.
5. Проверить, что первая версия не затёрта.

## 15. Критерии завершения MVP

Проект считается готовым, если:

1. Пользователь может зарегистрироваться.
2. Создаёт workspace и приложение.
3. Добавляет несколько страниц.
4. Собирает интерфейс из компонентов.
5. Редактирует свойства компонентов.
6. Использует вложенные контейнеры.
7. Перемещает компоненты через drag-and-drop.
8. Undo/Redo работает предсказуемо.
9. Документ сохраняется после перезагрузки.
10. Можно создать и выполнить разрешённый REST-запрос.
11. Таблица отображает полученные данные.
12. Кнопка запускает зарегистрированное действие.
13. Preview работает без инструментов редактора.
14. Опубликованная версия открывается по URL.
15. Изменение черновика не меняет публикацию.
16. Пользователи не получают доступа к чужим проектам.
17. Главные сценарии покрыты автоматизированными тестами.
18. Демо доступно без необходимости вручную создавать сложную конфигурацию.

**Финальный результат:** самостоятельная платформа визуальной разработки внутренних веб-приложений с реальным editor engine, data binding, API integration, versioning и опубликованным runtime.
